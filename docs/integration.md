# 将 KernAdapt 用于自己的负载

[文档首页](README.md) · [环境要求](compatibility.md) · [实验结果](benchmarks.md)

## 1. 从具体问题确定入口

如果数据库高并发时的主要问题是持锁线程延迟、锁交接或频繁迁移，先查看 LockCoop；如果多个工具工作流相互争抢 CPU，且完成时间依赖特定子进程返回，先查看 FlowCausal。需要随状态选择配置、记录决策并管理恢复时，再接入控制面。

先明确一个可测量的目标，例如事务吞吐、p95 延迟或平均工作流完成时间，同时记录共存任务需要获得的服务。不要只用总体 CPU 利用率判断应用是否获益。

## 2. 固定对照条件

记录代码版本、运行内核、实际调度器名称、CPU 范围、频率策略、数据库与数据设备、负载参数和运行时间。对照与改动使用相同条件，并交错运行多轮，保留每轮结果。

数据库实验还需要固定数据准备、重启、预热和 buffer pool 方式。工具回放需要记录会话数、工具命令、并发限制以及全部后台工作的结束条件。[结果说明](benchmarks.md)列出仓库采用的不同协议。

## 3. 逐步进入真实运行

先用离线演示理解决定与输出，再构建匹配内核的工具。加载调度器后检查实际运行状态，结束后确认恢复；命令见[构建与运行](构建与运行.md)。

LockCoop 的锁身份、持锁者确认和 CPU 范围影响哪些动作可以生效。FlowCausal 需要正确登记 cgroup、会话和工具调用。将项目接入自己的启动脚本时，应保持这些信息与实际进程生命周期一致。

## 4. 同时记录收益与代价

数据库至少报告吞吐、尾延迟及后台任务工作量；工作流同时报告平均完成时间和全部完成时间。保留没有获益的配置，以及退出、状态过期和观测缺失时的行为。由多项指标共同判断是否满足最初目标。

模型策略的选择质量和内核机制的端到端性能分别统计。`regret` 用来评价配置选择，不能直接换算为吞吐提升。

## 5. 分享结果或提出改进

使用[性能与复现表单](https://github.com/Lss-lmj/kernadapt-industry-2026/issues/new?template=performance.yml)，附环境、配置、基线、逐轮数据、统计脚本和现象描述。原始业务数据可替换为可公开的复现场景，但需要说明差异。

接口或机制修改按[贡献指南](../CONTRIBUTING.md)提供问题、设计、作用范围和恢复方式。这样其他使用者可以判断改进是否适用于自己的环境。
