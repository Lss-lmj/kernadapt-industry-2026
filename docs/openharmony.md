# OpenHarmony 系统接入设计

[项目首页](../README.md) · [开发设计文档](开发设计文档.pdf) · [环境与兼容性](compatibility.md)

KernAdapt 面向混合负载下的系统资源管理：数据库事务需要及时释放锁，工具工作流需要关键子进程完成，后台任务需要持续获得服务。接入设计以采用 Linux 内核的 OpenHarmony 系统为对象，把应用目标、用户态资源决策与内核调度分开组织。

## 1. 系统位置与职责

| 层次 | 输入和输出 | 对应模块 |
| --- | --- | --- |
| 应用与工具运行器 | 业务目标、会话身份、工具调用边界、吞吐与响应时间 | 应用结果采集、会话登记 |
| 用户态资源管理 | 根据状态比较配置，限制执行范围，记录结果和恢复条件 | `src/agent/` |
| 同步与任务观测 | 锁身份、可信持锁者、实际阻塞、唤醒与退出 | LockCoop 观测库、FlowCausal 登记与事件处理 |
| Linux 调度后端 | 按预算推进持锁者，选择后继 CPU，核算会话服务 | `src/lockcoop/`、`src/flowcausal/` |
| 产品与板级环境 | CPU 拓扑、驱动、运行内核、工具链和访问权限 | 目标产品的构建与启动配置 |

这里的服务边界描述集成方式。仓库内的运行入口是 Python 控制面、HTTP 运行时、C 加载器与 BPF 程序；接口和源码位置见[系统架构](architecture.md)及[代码索引](代码与脚本索引.md)。模型只参与配置决策，单次调度事件不等待模型返回。

## 2. 内核版本与板级组件

内核选择同时取决于板卡驱动、OpenHarmony 内核组件和项目使用的 sched_ext/BPF 接口。OpenHarmony 的[Linux 内核移植说明](https://github.com/openharmony/docs/blob/master/zh-cn/device-dev/porting/porting-linux-kernel.md)将通用内核、芯片平台代码与系统内核组件分开说明；文中的历史示例用于解释移植关系，实际组件以产品分支为准。

[Linux 6.12 sched_ext 文档](https://docs.kernel.org/6.12/scheduler/sched-ext.html)包含调度类、BPF、BTF 及配置项说明。6.12 提供 sched_ext，并不意味着任意较新 sched_ext 程序可以直接用于该版本。仓库归档实验包含 Linux 6.17；函数、结构体、回调和生成头文件按所用内核源码匹配。

| 配置项 | 在接入中的作用 |
| --- | --- |
| 产品分支与板卡型号 | 决定设备树、驱动、启动方式及系统组件 |
| 运行内核与配置 | 决定 sched_ext、BPF、BTF 和观测事件是否可用 |
| 完整内核工具树 | 为加载器和 BPF 程序提供匹配的构建接口 |
| 编译目标与工具链 | 保持用户态程序、观测库和目标 ABI 一致 |
| CPU 与 cgroup 范围 | 确定允许改变的任务集合和可用处理器 |

构建脚本使用专用 Linux 工作树，不负责替换产品镜像或合并板卡驱动。使用入口和依赖见[构建与运行](构建与运行.md)。

## 3. 同步语义与持锁者确认

LockCoop 的锁身份需要区分地址空间、同步对象和生命周期。进程内相同虚拟地址与不同进程中的相同地址不能直接视为同一把锁；共享同步对象则需要按共享关系识别。

OpenHarmony musl 的[普通 mutex 快速路径](https://github.com/openharmony/third_party_musl/blob/master/src/thread/pthread_mutex_lock.c)使用锁状态值。不能把普通 mutex 的锁字解释为 glibc 特定路径中的持锁线程标识。futex 唤醒事件也只能提供唤醒关系，不能单独证明所有权。

设计上按信息条件选择动作：

- 有可信所有权、实际等待和剩余预算时，LockBoost 才能延长相应持锁者的执行时间片。
- 同锁执行历史和目标 CPU 条件满足时，LockNest 选择后继执行位置；该动作独立检查位置是否有效。
- 所有权不明、任务退出、记录过期或预算耗尽时，相应优化不生效，并回到普通调度路径。

[同步观测头文件](../src/lockcoop/src/sched_ext/include/scx/lockcoop_user_sync.h)与[共享 BPF 状态](../src/lockcoop/src/sched_ext/include/scx/lock_observe.bpf.h)给出代码层的事件和状态定义。

## 4. 工具工作流与会话

工具运行器登记会话、cgroup 和工具调用代际。FlowCausal 结合实际阻塞事件识别影响工具返回的进程，维护 fork、唤醒、退出及调用结束后的状态。进程亲缘关系用于恢复来源，实际阻塞用于确认返回依赖。

会话之间按服务约束组织调度，会话内部可以给有效等待对象有限的提前运行机会。实际 CPU 消耗继续计入所属会话；配额、并行宽度和提前运行预算分别限制资源使用。该设计适用于本地 CPU 可见的工具阶段，模型推理和远程服务等待需要单独计时。

## 5. 控制面、权限与恢复

控制面先形成状态摘要和目标，再比较结构化配置。执行前检查动作参数、角色能力、作用范围与恢复条件；执行记录连接输入、选择、实际动作和观测结果。

普通查询、策略选择与特权加载应具有明确职责。凭据不进入配置样例和仓库；运行时服务的访问范围由部署环境约束。若配置无法应用，或运行结果不符合约束，执行流程记录原因并按对应动作恢复。完整接口见[项目设计文档](开发设计文档.pdf)。

sched_ext 自身的退出机制与控制面的恢复动作分开处理：加载器结束、调度器出错或任务长时间无法推进时，sched_ext 可恢复默认调度；控制面仍需恢复自身修改过的资源配置和运行记录。具体内核行为以相应版本的[官方说明](https://docs.kernel.org/6.12/scheduler/sched-ext.html)为准。

## 6. 应用场景与观察指标

| 场景 | 调度关注点 | 同时观察的指标 |
| --- | --- | --- |
| 数据库与后台计算共置 | 持锁者延迟、锁交接、CPU 放置 | 事务吞吐、p95 延迟、后台完成工作量 |
| 多工具工作流并发 | 实际返回依赖、会话 CPU 服务 | 平均完成时间、全部完成时间、会话 CPU 消耗 |
| 多类负载阶段切换 | 配置组合、约束、保持或恢复原配置 | 配置选择质量、效用、约束违反及恢复记录 |

ARM64、x86 和 RISC-V 数字按对应 Linux 实验环境报告。架构名称和目标系统名称分别记录，不能仅凭处理器架构推断 OpenHarmony 上的性能。各批次、基线与计算方式见[实验结果说明](实验结果说明.md)。
